# NidhiRakshak — Pre-Disbursement Risk Prioritization & Milestone Guardrail
### Internal Hackathon Prototype (SIH26102)

A live, clickable demo of an AI-assisted pre-disbursement risk prioritization
platform for MPLADS milestone review. NidhiRakshak is a prototype, not an
official Government of India service and does not claim live PFMS/e-SAKSHI
access or payment-blocking authority.

## Run it (zero setup)

Everything in this directory is static HTML/CSS/JS with the dataset already baked in
as a JS file — **no server, no build step, no internet connection required.**

Just open `index.html` in any browser (double-click it, or drag it into
a Chrome/Edge/Firefox window). The home screen has a no-login role switcher for
MP, State Nodal Authority, District Authority and MoSPI.

If your browser blocks local file access for any reason, you can also serve
the project locally in one line:
```bash
python3 -m http.server 8000
# then open http://localhost:8000
```

## Pages

1. **Role dashboards** (`index.html`) — switch instantly between MP,
   State Nodal Authority, District Authority and MoSPI views over the same data.
2. **State & District** (`state.html`) — drill down from state → district →
   individual MPs.
3. **MP Dashboard** (`mp.html`) — investigation-style searchable list of all
   MPs. Clicking an MP opens a dedicated dashboard page.
4. **MP Detail Dashboard** (`mp-detail.html`) — individual MP fund-utilisation
   profile and flagged projects.
5. **Investigation Queue** (`investigation.html`) — filterable, sortable list
   of every flagged work; click through to a full deep-dive per work showing
   every possible flagging reason (triggered or not) with its weight. Includes
   human-review buttons that persist demo feedback in the browser.
6. **Pre-Disbursement Guardrail** (`guardrail.html`) — select a work and
   proposed milestone, then run peer comparison, rule checks, verification and
   anomaly scoring to receive a Low / Medium / High review recommendation with
   human-readable reasons.
7. **Geo Registry** (`geo.html`) — geo-tagged asset registry surface with
   asset, satellite preview, boundary and risk layers per project.
8. **Data Sources** (`data.html`) — switch between Demo, Real and Combined
   data views across every page.
9. **Feedback Log** (`feedback.html`) — searchable column-based list of every
   project marked Reviewed or False Positive, with restore actions.
10. **Model & Accuracy** (`methodology.html`) — pipeline explanation,
   accuracy/precision/recall/F1/ROC-AUC, confusion matrix, feature
   importance, and known limitations.
11. **PDF Ingestion** (`ingest.html`) — upload a state nodal-agency work
    submission (PDF or text) and watch it get parsed client-side into
    candidate work records, staged for human review before joining the ledger.

## Prototype-enabled roadmap features

Three capabilities that used to sit in "Future Scope" now run end-to-end in
the demo, clearly labelled as running on synthetic or client-side data rather
than live government systems:

- **Cross-scheme data integration (MGNREGS, state schemes).** `pipeline/detect_anomalies.py`
  generates a synthetic MGNREGS/state-scheme feed and matches it against MPLADS
  works by district + asset category + cost window, producing a new explainable
  `CROSS_SCHEME_DUPLICATE` flag. See the "Cross-scheme data integration" panel on
  the Data Sources page and `data/cross_scheme.json`. Going live needs API/data-sharing
  access from the MGNREGS nodal ministry and state implementing departments.
- **Satellite / geo-tag verification for large civil works.** Works at or above
  ₹10 lakh get a deterministic simulated satellite-verification check (confirmed /
  mismatch / pending) shown on the Geo Registry page and in each project's geo panel.
  Going live needs a licensed satellite-imagery/change-detection provider.
- **Automated PDF ingestion from state nodal agency submissions.** The new PDF
  Ingestion page extracts text from an uploaded PDF (via pdf.js, entirely in-browser),
  parses candidate work rows, and stages them for review. It handles text-based PDFs;
  scanned/photographed submissions would need an OCR step in front of it in production,
  and the review queue would write into the ledger via API instead of browser storage.

## What's real vs. synthetic

- **Real:** MP names, states, constituencies, and MPLADS allocated fund
  limits — sourced from the published government allocation list
  (`Allocated_Limit_for_Honble_MPs.csv`).
- **Synthetic (clearly labelled):** individual work-level records — costs,
  dates, agencies, statuses — generated by `pipeline/generate_dataset.py`
  since per-work public data wasn't available for this prototype. Every
  synthetic work row carries `record_source = SYNTHETIC_DEMO_DATA` and, for
  benchmarking only, a `synthetic_ground_truth_fraud` flag used to score
  detector accuracy against a known answer key (see Methodology page).

The **Real data** view intentionally contains only the published MP roster and
allocation limits. Since no official per-work transaction file is included,
it shows zero works instead of presenting synthetic work records as real.
The **Combined** view joins the two layers by `mp_id`.

## Regenerating the data

```bash
cd pipeline
pip install pandas numpy scikit-learn --break-system-packages
python3 generate_dataset.py      # builds mplads_work_data.csv from the 18th Lok Sabha allocation roster
python3 detect_anomalies.py      # runs the detector + cross-scheme matcher, writes ../data/*.json
python3 build_site_data.py       # bundles ../data/*.json into ../assets/data.js
```
Then copy `assets/data.js`, `assets/app.js` and `assets/style.css` into `public/assets/`
so both the direct-open and dev-server paths stay in sync.

## Detection approach

Rule-based checks (12 explainable flags: low utilisation, cost inflation,
excess delay, agency concentration, duplicate/vague descriptions, round-number
costs, year-end rush sanctions, work-splitting, shell-agency patterns, stalled
status, cross-scheme duplicate funding) combined with an Isolation Forest
anomaly layer into a single 0–100 composite risk score. Full detail on the
Methodology page.
